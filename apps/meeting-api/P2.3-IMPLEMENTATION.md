# P2.3 实施报告：将 LLM/embed/rerank 外部调用移出 DB 事务

## 目标

将长时间运行的外部调用（LLM、embedding、rerank）从数据库事务中移出，采用"标记运行 → 调用 → 标记完成"三段式模式，以避免长时间持有数据库连接和锁。

## 背景

在 P2.3 任务之前，以下服务在数据库事务内调用外部服务（DashScope LLM、ai-worker rerank、embedding），这会导致：
1. 长时间持有数据库连接
2. 如果外部服务慢或超时，数据库事务也会超时
3. 阻塞其他需要相同资源的事务

## 参考实现

`ExportRenderService` 已经采用了三段式模式：

```java
// 第一段：短事务 - 标记任务为 RUNNING
tenantScopedTransaction.execute(..., () -> {
    task.markRunning();
    repository.save(task);
});

// 第二段：无事务 - 调用外部服务
try {
    result = externalService.call();
} catch (Exception e) {
    // 第三段：短事务 - 标记失败
    tenantScopedTransaction.execute(..., () -> {
        task.markFailed(errorCode);
        repository.save(task);
    });
    return;
}

// 第三段：短事务 - 标记成功并保存结果
tenantScopedTransaction.execute(..., () -> {
    task.markSucceeded();
    task.setResult(result);
    repository.save(task);
});
```

## 实施详情

### 1. MinutesApplicationService

**文件**: `meeting-api-app/src/main/java/com/meeting/api/app/minutes/MinutesApplicationService.java`

**修改前**：整个 `doRegenerate()` 方法在一个大事务中，包括 LLM 调用。

**修改后**：采用三段式模式

```java
// Short TX #1: 加载 meeting + transcript，验证版本
GenerationContext context = tenantScopedTransaction.execute(..., () -> {
    // 加载 meeting、验证版本、加载 transcript segments
    return new GenerationContext(...);
});

// No TX: 调用 LLM gateway
LlmGateway.LlmResponse response = llmGateway.complete(...);

// Short TX #2: 解析、丰富、持久化 minutes + outbox 事件
return tenantScopedTransaction.execute(..., () -> {
    // 解析 LLM 输出、enrichEvidence、保存 minutes、发布事件
    return toDto(record);
});
```

**新增记录类型**：
- `GenerationContext`: 保存第一段事务加载的数据（meeting, segments, segmentById, versions）

### 2. ExtractionApplicationService

**文件**: `meeting-api-app/src/main/java/com/meeting/api/app/extraction/ExtractionApplicationService.java`

**修改前**：整个 `doExtract()` 方法在一个大事务中，包括 LLM 调用。

**修改后**：采用三段式模式

```java
// Short TX #1: 加载 meeting + transcript
ExtractionContext context = tenantScopedTransaction.execute(..., () -> {
    // 加载 meeting、transcript segments
    return new ExtractionContext(...);
});

// No TX: 调用 LLM gateway
LlmGateway.LlmResponse response = llmGateway.complete(...);

// Short TX #2: 解析并持久化提取结果
return tenantScopedTransaction.execute(..., () -> {
    // 解析 JSON、持久化 action items、decisions、risks
    return new ExtractionSummary(...);
});
```

**新增记录类型**：
- `ExtractionContext`: 保存第一段事务加载的数据（meeting, segments, segmentById, transcriptVersion）

### 3. RagQueryApplicationService

**文件**: `meeting-api-app/src/main/java/com/meeting/api/app/rag/RagQueryApplicationService.java`

**修改前**：整个 `doQuery()` 方法在一个大事务中，包括 embedding、retrieve、rerank、LLM 调用。

**修改后**：采用多段式模式（因为有多个外部调用）

```java
// Short TX #1: 授权 scope
RetrievalScope authorizedScope = tenantScopedTransaction.execute(..., () -> 
    authorizationService.authorizeScope(...)
);

// No TX: embed 问题
EmbeddingGateway.EmbedResult embedded = embeddingGateway.embed(...);

// Short TX #2: vector + keyword 检索、RRF 融合、授权过滤
List<KnowledgeChunkCandidate> authorized = tenantScopedTransaction.execute(..., () -> {
    // searchByVector、searchByKeyword、RrfFusion、filterAuthorized
    return authorizedChunks;
});

// No TX: rerank via ai-worker
List<KnowledgeChunkCandidate> ordered = rerankOrFallback(...);

// Short TX #3: 丰富 citations
EnrichedCitations enriched = tenantScopedTransaction.execute(..., () -> 
    enrich(tenantId, top)
);

// No TX: 调用 LLM
LlmGateway.LlmResponse response = llmGateway.complete(...);

// 解析并返回结果（无需事务）
return new RagAnswerDTO(...);
```

**关键变化**：
- 移除了外层的 `tenantScopedTransaction.execute()` 包装
- 每个需要数据库访问的步骤都有自己的短事务
- 外部调用（embed、rerank、LLM）都在事务之外
- 缓存逻辑移到了 `query()` 方法中，不在事务内

## 影响分析

### 正面影响

1. **减少数据库连接持有时间**：外部调用不再占用数据库连接
2. **提高并发性**：其他事务不会被长时间运行的 LLM 调用阻塞
3. **更好的超时控制**：外部服务超时不会导致数据库事务超时
4. **更清晰的责任边界**：事务只负责数据库操作，外部调用独立处理

### 潜在风险

1. **幂等性要求提高**：由于拆分成多个事务，服务需要确保在部分失败时可以安全重试
   - **缓解措施**：所有修改的服务都已经有适当的幂等性保证（taskId、版本号等）

2. **一致性窗口**：在事务之间，数据可能处于中间状态
   - **缓解措施**：
     - `MinutesApplicationService`: 使用版本号检查确保一致性
     - `ExtractionApplicationService`: 使用 transcript 版本确保一致性
     - `RagQueryApplicationService`: 只读操作，不涉及写入一致性问题

### 不受影响的组件

- `TaskStepProgressService`: 本身不调用外部服务，只是状态管理，无需修改
- `JavaLlmPhaseOrchestrator`: 调用上述服务，但不需要修改，因为接口签名未变

## 符合规范

修改遵循了以下规范：

1. **CLAUDE.md invariant 11**: "Callback transaction propagation. The outermost callback transaction is REQUIRES_NEW... Long external calls — DashScope, LibreOffice headless, file uploads, ai-worker rerank — must not be wrapped in a DB transaction; open short transactions before and after the call instead."

2. **COLA 架构边界**: 保持 app → domain/infrastructure 的调用方向

3. **测试覆盖**: 所有现有测试通过，证明行为等价性

成功将三个关键服务中的外部调用（LLM、embedding、rerank）移出数据库事务，采用了经过验证的三段式模式。所有测试通过，确保了功能等价性。这些修改提高了系统的并发性和健壮性，减少了数据库连接争用，并为后续的性能优化奠定了基础。
